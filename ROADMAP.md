### ◆◆ PRODUCT THESIS (the organizing principle — read this first) ◆◆

**"The conversation is the product; the app is the back office."**

Shadow's **primary interface is a CHATBOT** the user talks to like texting a bookkeeper — ideally **in a channel they already live in** (Slack, email, text). They feed it documents, ask questions ("how much did I spend on AWS last month?"), request reports, set reminders, ask it to send follow-ups — and **never have to open the app if they don't want to.** The full app (tabs, GL, reports, journal entries) still exists — as the **back office / CPA + power-user surface** — but it is **OPTIONAL, not the main way the user interacts.**

**Why.** The target customer (a small-business owner) doesn't want to **learn accounting software** — even *simple* software. They lack the time/bandwidth and would rather pay someone to handle it. QBO's flaw isn't that it's hard; it's that it **must be operated at all.** Shadow's wedge is **removing the operating**: it *feels* like texting a bookkeeper because functionally it **is** one. The bot is the **TRANSLATOR between human and accounting.**

**THE CARDINAL PRINCIPLE — the interaction boundary (what the bot may and may not ask):**
- ✅ **OK to ask the user — human questions about their business:** *"What was this $400 for?", "Is this a subscription?", "Business or personal?", "Which project is this?"*
- ❌ **NEVER ask the user — accounting decisions or jargon:** *"Should we credit the payable?", "Is this 6100 or 6200?",* debits/credits, GL codes, journal-entry concepts. The bot translates the human answer into the accounting **silently. The user never sees a debit.** (This is the chat-side twin of **O77**'s "ask rarely, in plain language, let them state the category" — generalized into a hard boundary: human-language questions yes, accounting-language questions never.)

**What this reorganizes (re-weighting, not new mechanics):**
- **O80 (Shadow Assistant) is reframed from "a later vision feature" to the PRIMARY PRODUCT SURFACE** — the roadmap's **center of gravity**, not a nice-to-have. (Its layers — memory/reminders, proactive surfacing, conversational ledger Q&A, task execution, assistant framing — are the product, not an add-on.)
- **NEW implied item → CHANNEL INTEGRATION (O82):** deliver the bot **where the user already is** (Slack first; email/text later) so *"never open the app"* becomes literally true. (Subsumes/realizes the old O29 Slack-bot idea; ties the O56 invisible-controller inbox.)
- **App declutter is SECONDARY** (fewer tabs, hide the accounting machinery, organize around **user questions** not accounting concepts). It matters for the **optional** deep-dive, but **the bot carrying the load is the bigger lever** — don't let UI polish outrank the conversational surface.
- **O81 (bot safety) rises in importance:** if the bot is the **primary high-power interface** (it both reads everything and acts on the books), guardrails / anti-prompt-injection matter **even more** — it's not an edge surface, it's the front door.

**Dependency order toward this vision:** **O78** (persistence — bot actions must stick ✅ C112) → **O80** (assistant capability: memory/reminders/proactive/send-on-behalf) → **O82 channel integration (Slack)** → **O81** (safety hardening for primary-interface use) → **app declutter** (secondary). The **trust layer (O60 / O49 / O50) underpins all of it** — the bot's answers and actions must be **correct + verifiable**, because a conversational bookkeeper that's confidently wrong is worse than no bookkeeper. The **scalability constraint on O80 layer 3** (answer by QUERY, not ingestion) is a hard requirement of this thesis, not an optimization — a primary interface must work at any client's history size.

#### ◆ Thesis addendum — load-bearing dependencies + open questions (so the thesis is honest, not just aspirational)

The vision's direction is sound; this names what it RESTS ON, so the build order stays honest.

1. **The trust layer is a DEPENDENCY of this vision, not a sibling feature.** Conversation-as-interface **hides the accounting from the user — which also hides the ERRORS from the user.** A QBO user at least *sees* their books and might catch a miscategorization; a Shadow user sees almost nothing, so they've **surrendered oversight** — which means the books must be **provably correct, because no human is checking them at the surface.** So the trust layer (**O60** completeness / **O49** confidence-flagging / **O50** CPA-review surface) is **what makes the invisible interface SAFE to ship.** *The less the user sees, the higher the bar on silent correctness.* **Implication:** build the trust layer **before (or alongside)** the polished conversational interface — a beautiful chat over books that can be silently wrong is **dangerous, not magical.**

2. **The CPA-review loop defines the BUSINESS SHAPE.** "CPA-reviewed monthly" is the resolution to #1 — AI does ~95%, a licensed CPA backstops the consequential ~5%. Right model for safety, but it means: **(a)** Shadow is an **AI-leveraged SERVICE, not pure infinitely-scalable SaaS** — scale is gated by how many clients one CPA can review; **(b)** the trust layer's job is to **REDUCE the per-client review burden** (flag only what needs a human look) so one CPA reviews **50 clients instead of 5.** So **O50 + O49 aren't just trust features — they're the SCALE mechanism.** Clear-eyed: this is a **high-margin AI-services business whose ceiling rises as the trust layer improves**, not (yet) a zero-marginal-cost SaaS.

3. **The app is the TRUST / REASSURANCE surface, not just a power-user fallback.** A pure-chat black box gives a new user no way to build confidence it's working (*"I sent it stuff… is it doing anything? are my books actually right?"*). The app — showing **real, balanced books** — is the **PROOF layer that makes people trust the conversation, especially early.** **Reframe the app's role** (refining the thesis above): not "optional power-user thing" but **"the reassurance/proof surface that earns trust in the invisible service."** Users may rarely open it, but it **must exist and must look credible** when they do. (Nuance on the "app is secondary" point above: secondary as a *daily interaction surface*, **load-bearing** as a *trust surface*.)

4. **OPEN QUESTION — who is the PRIMARY customer? (currently undecided: "broad SMB").** Unresolved, and it **cascades into nearly everything** — flagging as a real decision, not a detail:
   - **Channel depends on it:** tech-adjacent (agencies/startups) live in **Slack**; most SMBs (contractors, restaurants, solo shops, retail) live in **email and text**, not Slack. The thesis's **"Slack first" assumption may be wrong** for a broad-SMB/trades audience — **channel (O82) should follow the actual customer** (likely **email/SMS-first** for non-tech SMB).
   - **Segment shifts the specifics:** the **bot's questions**, the **default chart of accounts**, and even **pricing** all change by segment (a restaurant's books ≠ an agency's ≠ an e-comm seller's).
   - **ACTION:** pin down a **beachhead segment** (even if broad later) — it sharpens channel, onboarding, COA defaults, and the bot's domain knowledge. **"Broad SMB" is a fine launch stance but an expensive thing to leave permanently fuzzy.**

   **Net:** these don't change the vision's direction — they make the build order honest: **trust layer underpins the invisible interface · CPA-review defines scale · the app earns trust · the customer segment (open) drives channel + bot specifics.**

### ★ KEY DESIGN DIRECTION — The Clarification Loop (the trust layer and the conversation are ONE loop)

**Decided direction (resolves the "how does the Review queue actually get worked / who resolves what" question raised when O50 shipped, C116).** The trust layer (detect) and the conversational interface (ask/resolve) are **not two systems — they're one loop.** This is exactly how a real accountant/CFO operates: when they lack the info to book something, they ask the client a quick follow-up. Shadow **automates the chase.**

**The loop:**
1. **DETECT** — the AI processes a transaction, is uncertain → **O49** flags it (low-confidence-and-material), it lands in the **O50** review queue.
2. **ASK** — if resolving needs info **only the CLIENT has**, the bot asks a **plain-language** question — *"What was this $400 Hartford payment for?"* — ideally **in the channel they live in** (Slack/email/text — **O82**), at goal state.
3. **RESOLVE** — the client answers conversationally (*"business insurance"*) → the flag **auto-resolves**, the txn books correctly (the bot translates the human answer into the accounting — it never shows them a debit).
4. **LEARN** — the AI learns from the answer (**O64–O68**) → next time it **doesn't ask** (the questions decay; "never make the user correct the same thing twice").

**This makes the Cardinal Principle operational:** the bot asks **HUMAN** questions about the business (*"what was this for?", "is this a subscription?"*), **NEVER accounting** questions. The client experiences *"my bookkeeper texted me a quick question"* — the exact real-CFO relationship Shadow sells.

**Implications:**
- **Resolves the Review-tab visibility/ownership question:** the CPA (Alex) sees the **oversight queue** (O50); **resolution flows through the conversation, mostly self-serve.** Alex steps in only for items needing **accounting JUDGMENT** (capitalize vs expense, a GAAP treatment — which the client couldn't answer anyway). The queue is **largely self-resolving → scalable** (one CPA backs many clients — the economic unlock O50/O49 exist to create).
- **The bot is the INFORMATION-GATHERING ARM of the service**, not just a query interface. A real bookkeeper's core job is **chasing clients for context**; this automates the chase. (Ties **O80** layer 2 *proactive surfacing* + the *send-on-behalf* capability.)
- **It's the operational glue that makes "conversation is the product" real:** **O49** (detect) → **bot** (ask, via **O82** channel) → **books** (resolve) → **O64–O68** (learn). One organism, not a pipeline of features.
- Reframes **O77** (clarification model): the "ask rarely, in plain language, let them state it" model is *this loop at the upload moment*; O49→bot is *the same loop post-booking*. Same discipline, two entry points.

**Sequencing:** goal-state synthesis — depends on **O49 (✅ C114)**, **O80** (assistant can ask/act), **O82** (channel), **O64–O68** (learning). **Nearer-term slice — ✅ SHIPPED C117:** the **"Ask the client"** action on an O50 flag drafts a plain-language, jargon-free question (Cardinal-Principle-enforced; `src/lib/clarify.js` `draftClientQuestion`), and the client's answer maps to an account (`answerToAccount` — vendor-rule-aware) and **resolves the flag via the verified `reviewOverride`** (a vague answer → null → refuses to resolve). Shipped **without O80/O82**; the drafted question carries a structured `channel` payload so O82 can later auto-send + auto-ingest. **Remaining (O80/O82-dependent):** auto-send to the client's channel + auto-ingest the reply; deeper AI answer→account mapping; the O64–O68 learning write-back so the question decays.

### ★ STRATEGIC — The Trust Layer is product viability, not polish

**Framing question: "How would we catch a silent error — like the Riverside tax-into-revenue mistake (C83) — for a LIVE client?"** Today the honest answer is: **we wouldn't**, except by a manual SQL audit — which doesn't scale and isn't what we sell. A real client sees **"✓ booked"** and trusts it. So the trust layer is **the core of a CPA-staked product**: a CPA cannot sign off on books they can't verify without redoing them. **Correct-but-unverifiable books are unsellable.** This may matter **more than remaining functional features** — elevate accordingly.

**Four layers, in priority order:**
1. **Structural reconciliation / control totals — HIGHEST leverage (O60 + O59).** Reconcile to INDEPENDENT sources so math catches errors automatically, regardless of AI honesty: bank statement = cash ground truth; AR ties to GL; statements balance; categorized expenses = bank debits. KPMG-style reconcile-to-independent-source — an error like tax-in-revenue would surface as a non-tie. **(Note: the Riverside class specifically needs an "AR/revenue vs. what was billed" tie + a sales-tax-liability check.)**
2. **AI confidence + flag-when-unsure (O49).** The app must SURFACE uncertainty instead of silently guessing — e.g. *"unsure about the tax line on this messy invoice — confirm?"* Turns silent errors into surfaced questions. (The C83 follow-up — ask about an uncertain tax line — is an instance.)
3. **CPA review surface (O50).** A dashboard that surfaces only the suspicious ~5% (low-confidence, anomalies, non-reconciling) for human review, so **"CPA reviewed" ≠ "CPA redid everything."** Makes the human backstop SCALE — the economic unlock for the CPA-staked model.
4. **Anomaly detection (extends C50 + the learning layer O65–O68).** Proactive pattern-breaks flagged (tax rate changed, vendor amount spiked, a normally-taxed customer suddenly untaxed).

**Priority elevation:** the trust trio **O60 (P1) · O49 (P1) · O50 (now P1, was P2)** is the viability cluster — treat it as the spine the near-term roadmap serves, ahead of net-new functional features. O59 (capstone sim) is the at-scale proof of layer 1.

#### ◆ O60 — Document Completeness architecture (design)

**Two populations, two nets — both required for airtight completeness.** The guarantee must hold **NOW** on existing upload paths; the inbox is a future enhancement, not a prerequisite.

**Population 1 — Documents received** (what the client *sends*):
- Every document gets an **intake row with status the moment it enters, before processing** — regardless of channel (upload now; inbox/email/Slack later).
- **Terminal states only:** `recorded` / `held-for-review` / `rejected-with-reason`. A **catch-all** routes unhandled / unexpected / errored files to `held-for-review`, **never void** — no silent disappearance is possible.
- **Received-vs-resolved reconciliation:** `count(entered) == recorded + held + rejected`, at all times. Any doc not in a terminal state (or stuck `processing` past a threshold) is surfaced.

**Population 2 — Transactions that happened** (the bank/card statement as **ground truth**):
- Every bank-statement line must resolve to a journal entry **or** an explicit categorization. This catches **real transactions for which NO document was ever sent**.
- **Bank-line completeness check:** every imported line accounted for; any unresolved line surfaced.
- The bank statement is the **ultimate population control** — the independent record of what actually touched the money.

**Intake — phased:**
- **NOW:** enforce the Population-1 guarantee on the **existing upload paths** (intake row on upload, terminal-state enforcement, reconciliation check, catch-all for unexpected types). Don't gate completeness on new intake mechanisms.
- **LATER (vision — see O56):** an **inbox (email/Slack) as primary intake**. Its completeness value: the received-count lives **outside the app** (the mail server counts it) → an **independent control total** to reconcile against, plus an **immutable, timestamped audit trail**. A better front door for Population 1, layered on once it exists.

**The Completeness Dashboard:** surface **both** reconciliations to the CPA/client — *"X documents received, all accounted for (Y recorded, Z in review, W rejected)"* and *"all N bank lines resolved."* This is the demonstrable assertion that lets the signing CPA say **"I have everything," with proof**.

**Buildable now:** intake-row + terminal-state + reconciliation core (Population 1) and the bank-line completeness check (Population 2). **Future:** the inbox front door. Population 2 also ties to **O7** (event coverage) and is exercised at scale by **O59**'s control-sheet check.
