## 1. Project overview & tech stack

**Shadow CFO** is a single-page AI accounting/bookkeeping app for small-business owners: drop in a document (invoice, receipt, bank statement, contract) and the AI extracts it, codes it to the right GL account, books a balanced double-entry journal entry, and answers CFO-level questions in plain English.

- **Frontend:** React 18 + Vite. No routing library — views are switched via a `view` state string in the `ERP` component.
- **Backend:** Supabase (Postgres + Auth + Storage + Edge Functions). Postgres Row Level Security is the tenant-isolation boundary.
- **AI:** Anthropic Claude (Haiku classifier + Sonnet brain), proxied through a Supabase Edge Function so the API key never reaches the client.
- **Charts/tests:** dependency-free inline SVG (no recharts); Vitest for unit tests.
- **Styling:** all inline JS style objects. Dark auth screens; light app shell. Inter font, DM Mono for numbers. Accents: indigo `#4F46E5`, green `#039855`, amber `#DC6803`, red `#D92D20`.

The entire authenticated app lives in **`src/App.jsx`** (~4000+ lines). Views were progressively extracted into `src/components/views/*` and shared logic into `src/lib/*`, but `ERP` in `App.jsx` still holds nearly all state and is the source of truth via `ERPContext`/`useERP()` (~300 keys).

### Component hierarchy
```
AppWrapper          — auth state machine (session → companies → view routing)
  AuthScreen        — email/password login, signup, password reset
  CompanySetup      — first-run company creation (seeds COA, bank account, subscription)
```

## 3. Multi-tenancy & RLS

Isolation is enforced **at the database**, not the client. Every tenant table has four policies (`select`/`insert`/`update`/`delete`) of the form `using (public.is_company_member(company_id))`. `is_company_member` is `SECURITY DEFINER` so it can read `company_users` with RLS bypassed (avoids recursion and is fast). Migration `001` applies these in bulk to the core tables; later migrations add the same shape per new table.

- The **anon key is public by design** — RLS is the real boundary. Never rely on a client-side `.eq("company_id", …)` filter for security; it's for correctness/perf only.
- **Platform-admin bypass (Option A):** `is_company_member` returns true for platform admins (`PLATFORM_ADMIN_EMAILS`) so Support Mode works through the normal client. Support-mode actions are attributed to `Platform Admin - <email>` in the audit log.
- **UI-layer complement:** switching companies calls `resetCompanyState()` so no previous company's data bleeds into the next while the new data loads.

> When adding a company-scoped table, you MUST add a migration enabling RLS + the four `is_company_member(company_id)` policies. (This audit found `accounts` was missing it — fixed in `023`.)

## 4. Chart of accounts & the `system_role` scheme

Account **numbering convention** (helpers in `src/lib/gl.js`):
- `1xxx` Assets · `2xxx` Liabilities · `3xxx` Equity · `4xxx` Revenue · `5xxx`/`6xxx`/`7xxx`/`8xxx` Expenses.
- `glIsRevenue`, `glIsExpense`, `glIsBalSheet`, `glPLType` classify by the first digit.

**Authoritative expense accounts** (default codes — users may rename/renumber):
`6000` Salaries & Wages · `6100` Rent & Occupancy · `6200` Utilities · `6300` Marketing & Advertising · `6400` Travel & Entertainment (meals 50%) · `6500` Technology & Software · `6600` Office Supplies · `6700` Insurance · `6800` Professional Services · `6900` Depreciation & Amortization · `7100` Miscellaneous · `8000` Interest Expense.

**Why roles, not hardcoded codes:** users can renumber/rename accounts, so code never hardcodes `"6100"`. Each default account has a stable `system_role` (e.g. `rent_occupancy`, `travel_entertainment`). Resolve via `getAccountByRole(role)?.code` (or `rc(role)`/`rn(role)` inside `ERP`). The deduction tracker, recurring detection, and AI all go through roles so totals follow the company's actual accounts. The role↔code map lives in `DEFAULT_CHART_OF_ACCOUNTS` (`src/lib/constants.js`); `useAccounts` builds the live `byRole` index.

## 5. AI architecture

Two-stage pipeline, both calls through the **`ai-proxy`** Edge Function (`supabase/functions/ai-proxy/index.ts`):

1. **Intent classifier** (`classifyIntent`, `src/lib/ai.js`) — Haiku (`AI_MODEL_FAST`), ~150 tokens. Classifies the message (`ledger`/`contacts`/`rules`/`general`) to decide how much context to load.
2. **CFO brain** (`runAIBrain`) — Sonnet (`AI_MODEL`), up to 4000 tokens. Receives a system prompt with: today's date + current year, the COA, vendor rules, contacts, up to 80 ledger rows, a **live financial snapshot** (`buildFinancials`), the **learned client profile** (`client_ai_profile`), and a **sandbox statement**. Returns `{ reply, actions[] }`.

**ai-proxy** authenticates the caller's Supabase JWT (service-role client), enforces rate limits (**60 AI/hr**, **20 uploads/hr** per user via `bump_rate_limit`; `x-rate-kind: upload` header tags uploads), then forwards the unchanged Anthropic Messages payload to `https://api.anthropic.com/v1/messages` with the server-only `ANTHROPIC_API_KEY`. The client never holds an Anthropic key.

**Action sandbox** (`src/lib/aiCapabilities.js`): the AI may only emit whitelisted action types (`recode`, `void_invoice`, `delete_invoice`, `reverse_entry`, `add_rule`, `add_account`, `add_recurring`, `add_contact`, `navigate`, `render_chart`, `export_csv`, `render_summary`, …). The action loop refuses + logs (`ai_action_refused`) anything else, caps bulk deletes at 3, and every data-changing action is audit-logged.

**Reply parsing** (`runAIBrain` tail): the reply is scrubbed brace-balanced (`scrubLeakedActionJson`) so action JSON never leaks into the chat bubble; actions are recovered (`extractActionObjects`) even from malformed JSON. Inline charts/CSV/summaries render via `ChatRichOutput` and persist in `chat_messages.actions_taken`.

>
> **★ `091` WRITTEN 2026-09-15, ▶ HOLD — NOT APPLIED (O139, the line-account company guard). Run its probe (A) first; it is expected to say FAIL.**
>
> **★ MIGRATIONS APPLIED — the live state.** **Applied & verified live: through `061`, PLUS `063`** (`060` on 2026-08-08, `061` on 2026-08-09, **`063` on 2026-08-17**; all verified via catalog queries, not an HTTP 201). **Pending: `062`** (unknown_documents policy dedup — queued, unwritten).
>
> **RULE: every migration application gets its date recorded on this line, in the same docs commit that closes the session.** The repo records migration FILES; nothing in it records their APPLICATION, and there is no `supabase_migrations.schema_migrations` table to ask (see below — deliberately). So a file's presence proves only that it was written. Without this line every fresh session re-derives the answer, guesses wrong, and re-raises a migration as "still pending" that went live days ago. *(Cost already paid: `060` was flagged unapplied twice after it was live.)*

- Files live in `supabase/migrations/NNN_description.sql`, applied in numeric order. Wrap in `begin; … commit;`.
- **Idempotent**: `create table if not exists`, `drop policy if exists` before `create policy`, `add column if not exists`.
- Some numbers are intentionally absent from the repo (e.g. 016/017/020/024/025 were applied directly during development) — numbering is monotonic, not necessarily contiguous. New migrations take the next free number (the tree currently runs through `091` plus a dated `20260605_*` file, so the next free number is `092` — `062`, `065`, `067` are deliberately unused; see the ledger below). **Before choosing a number, `ls supabase/migrations/` and confirm it's unused** — a duplicate prefix silently breaks things (a duplicate `051` once caused a migration to be skipped; it was renumbered to `053`).
- Migrations are **not auto-run**; the user applies them in the Supabase SQL editor. Code that depends on a new table must degrade gracefully (try/catch, "table may not exist yet") so the app keeps working pre-migration.
- **NEVER run `supabase db push` (or `supabase migration up`) against this project.** There is **no `supabase_migrations.schema_migrations` tracking table** — migrations have always been applied manually (SQL editor / Management API), so the CLI has no record of what's live and would try to re-run the ENTIRE chain, including `000_baseline_schema.sql` (bare `CREATE TABLE`, unsafe on a live DB — see below). Migrations are managed manually by design; do not create a tracking table or introduce `db push`.
- **Apply AND verify in the SAME task, with the verification output in the report.** When you (or the user) apply a migration to production, immediately query the live DDL to confirm each object the migration creates/changes actually exists, and paste that query output into your report. The `053_signoff_reviewer_and_override.sql` report is the template: for each element (new columns, functions, policies, any data remap) run a read-only check (`information_schema.columns`, `pg_proc`, `pg_policies`, row counts) and show the result — never report a migration as "applied" on the strength of an `HTTP 201` alone. (Applying via the Supabase Management API SQL endpoint with the CLI's access token is the working mechanism; it runs raw SQL and does not touch any tracking table.)
- **★★ A PROBE THAT MUST ROLL BACK REPORTS THROUGH `raise exception` — AND THE MESSAGE MUST LEAD WITH THE FACT THAT IT IS NOT A FAILURE (recorded 2026-08-29, after it confused the operator on a live run).** Some checks can only be made by attempting the thing and watching it be refused (`071`, `076`). Those need two properties at once: **the probe row must never survive**, and **the verdict must be visible**. `raise exception` is the only construct giving both — it aborts the transaction AND prints — because `raise notice` does not reliably reach the Supabase editor.
  - **THE COST, PAID IMMEDIATELY: the editor renders it as `Failed to run sql query: ERROR: P0001: …`.** `P0001` is *"a function raised this deliberately"*, not a database error. But **a PASS displayed in red under the word *Failed* is the description contradicting the outcome** — the §9 defect this file is largely about, committed by the verification layer itself. `076`'s probe returned `PASS - the constraint refused role=member` and the operator still asked *"what about that one that appeared to fail?"*. That question is the evidence.
  - **THE RULE: LEAD WITH THE MESSAGE'S OWN NATURE, NOT WITH THE VERDICT.** `raise exception 'CHECK RESULT (not an error — this rolled back on purpose): %', verdict` — so the first words a reader sees explain the red, before they have to reason about an error code. **A verdict that needs a paragraph of context to be read correctly is one that will be misread by whoever runs it next.**
- **★★ VERIFICATION SQL IS ONE STANDALONE STATEMENT PER CHECK, EACH RETURNING A SINGLE VERDICT ROW (operator's standing preference, 2026-08-27).** Paste-ready, no editing. **The Supabase SQL editor displays ONLY THE LAST STATEMENT'S RESULT**, so a multi-statement block hides every verdict but the final one — silently, and in the direction of looking fine.
  - **COST ALREADY PAID — THREE CHECKS LOST IN ONE CHAIN (`074`/`075`):** *(1)* the convention of writing VERIFY blocks as `--` comments means stripping the prefix un-comments the PROSE too, producing SQL that dies on line one; *(2)* last-statement-wins hid three of four SELECTs in `074` block (b), leaving only a raw count with no verdict; *(3)* it hid `075`'s `anon` privilege check **entirely — even after that block was restructured to return a result set** — because the file was pasted whole. **A check whose result the operator cannot see is a check that was not run.**
  - **THE RULES:** compute the verdict IN SQL (`case when … then 'PASS - …' else 'FAIL - …' end as verdict`) rather than making the reader interpret raw values · **never report a verdict via `RAISE NOTICE`/`RAISE WARNING`** — the editor does not reliably surface either · **if a check genuinely needs a transaction with a rollback, SAY SO and give it as ONE self-contained block**, never as loose statements, because the rollback is what makes it safe and a statement pasted alone commits.
  - **FOR PRIVILEGE CHECKS, USE `has_function_privilege(role, 'schema.fn(args)', 'EXECUTE')`, NOT A REGEX OVER `proacl`.** It is **Postgres's own resolver** — the code path the executor consults — so it accounts for PUBLIC grants and role inheritance, which a `proacl LIKE '%anon=%'` match silently misses. **An ACL can read clean and still grant EXECUTE through PUBLIC.** *(This is why `075`'s catalog check was weaker than it looked; the single-statement replacement is `supabase/verify/075_anon_denied.sql`.)*
  - **RUNNABLE COMPANIONS LIVE IN `supabase/verify/`, NEVER IN `supabase/migrations/`** — a file sharing a migration's numeric prefix is how a duplicate `051` once caused a migration to be SKIPPED. Nothing in `supabase/verify/` is ever applied as a migration.
  - **When handing SQL over via `pbcopy`, verify the clipboard matches the file** (`shasum`), so a truncated copy is caught before it is pasted into production.
- Show the SQL and get confirmation before writing code that depends on a new table.
- **★★ THE CHAIN DOES NOT REPRODUCE LIVE FUNCTIONS — ANY `create or replace` STARTS FROM `pg_get_functiondef` (recorded 2026-08-17, O108).** The repo holds **five** definitions of `seed_company_accounts` (`000`,`008`,`009`,`038`,`044`) and the highest-numbered, **`044`, was never applied and could not be** — it inserts an `account_type` column that does not exist on `public.accounts` (confirmed live: 0 rows in `information_schema.columns`). So the reproducibility claim below is **TRUE FOR TABLES, FALSE FOR FUNCTIONS**: replaying the chain would install a function body that has never been live.
  - **THE RULE: `create or replace` of a live function is a COPY operation, never a reconstruction.** Pull `select pg_get_functiondef(oid) from pg_proc where proname = '…'`, paste it verbatim, make the smallest possible edit, and **prove the diff mechanically** — write both versions to files and `diff -u` them, don't eyeball it. Cost already paid: `063` was first written from `009` with its middle reconstructed from `constants.js`; it would have **dropped 17 accounts and repointed 11 codes** (`2400` Lease Liability → Notes Payable, `6300` Marketing → Repairs, `3000` Common Stock → Owner Equity) plus role renames that break `getAccountByRole` for every new company. It was caught only because the operator asked for a diff against live instead of accepting the file.
  - **Corollary: the function's ACL is not in the repo either.** `pg_get_functiondef` does not emit grants, and `create or replace` PRESERVES them — so never re-assert a grant you have not read. `009`/`044` both revoke `anon`; live still carries `anon=X` (O108 finding 2, → `069`).
- **`000_baseline_schema.sql` is the schema baseline** (a schema-only `pg_dump` of live). The chain is now reproducible: empty DB → `000` → `001…036` recreates the live schema (see §11). `000` uses bare `CREATE TABLE` (no `IF NOT EXISTS`) — **never run it against the existing production database; it is for an EMPTY database only.** Migrations `001…036` are idempotent (create-or-replace functions; if-not-exists tables/columns/indexes; drop-if-exists+create policies/triggers; drop+add constraints), so they re-apply cleanly on top of `000`.

## 7. Key architectural decisions (and why)

- **Soft delete** (`deleted_at`/`deleted_by`) instead of hard delete — recoverable, preserves the audit trail. All read queries filter `deleted_at IS NULL`; client logic also excludes `status === "voided"`/`"deleted"`.
- **Atomic journal writes via RPC** (`post_journal_entry`) — guarantees balanced, all-or-nothing double-entry writes. `persistJournalEntry`/`bookToDb` is the single write path; `source` is normalized to the CHECK-allowed set there.
- **`system_role` indirection** — see §4. Survives user renumbering.
- **Server-side AI key + rate limiting** — the edge function is the only place the Anthropic key lives; limits prevent abuse/runaway cost.
- **Adaptive `client_ai_profile`** — the AI gets smarter per client (vendor→GL memory, spending patterns) without retraining.
- **State reset on company switch** — UI-layer isolation complementing RLS.
- **Inline SVG charts** — zero new dependencies, full control, no bundle bloat.

## 8. Patterns to follow

- **New tenant table** → migration with RLS + the four `is_company_member(company_id)` policies; map columns back to the app shape in `loadAllData`; add to `resetCompanyState`.
- **New booking path** → go through `bookToDb`/`persistJournalEntry` (never insert journal entries directly). It handles `source` normalization, doc relinking, profile learning, and recurring detection.
- **GL lookups** → `getAccountByRole`/`rc`/`rn`, never a hardcoded code string.
- **New AI capability** → add the action to `AI_ALLOWED_ACTIONS`, document it in the prompt, add a handler in the action loop, and `logAI` it.
- **Mutations** → call `logAudit`/`logAI` so it lands in `audit_log`.
- **User input destined for HTML/CSV** → escape it (`SendInvoiceView` `esc`); use the `insights.js` CSV helpers for exports.
- **Dates** → `fmtDate` (`src/lib/format.js`); store `YYYY-MM-DD`.

## 9. Anti-patterns to avoid (mistakes already fixed)

- ❌ Hardcoding GL codes (`"6100"`). ✅ Use roles.
- ❌ Inserting journal entries outside `post_journal_entry`. ✅ Single RPC path.
- ❌ Trusting client-side `.eq("company_id")` as security. ✅ RLS is the boundary.
- ❌ Letting AI action JSON render in the chat reply. ✅ Brace-balanced scrub + separate `rich` array.
- ❌ Auto-navigating when rendering a chart. ✅ Only the "View full report" button navigates.
- ❌ Date filters that include the prior year for "this year"/deductions. ✅ Inject current year; filter `startsWith(year)`, exclude voided/deleted.
- ❌ Description/keyword matching for deductions or duplicates. ✅ GL-code + role for deductions; vendor-normalize + amount/date windows for duplicates.
- ❌ Leaving company-scoped state set across a company switch. ✅ `resetCompanyState`.
- ❌ Un-escaped user input in generated HTML (`document.write`). ✅ `esc()`.
- ❌ **Deriving matchability / openness / settledness from a denormalized status FLAG (`type`, `payment_status`, `matched`).** ✅ **Derive truth from the live GL entries.** This was the single root cause behind ~10 rounds of bank-matching bugs (O73): a `type` string that drifted from `"revenue"/"expense"` starved the candidate set AND gated a `type`-based early-return that skipped the deterministic matcher entirely; a stale `payment_status="collected"/"paid"` (from a prior clearing later reversed) both excluded genuinely-open invoices and made the clearing post silently skip (`isTransition` false). The flags are caches that go stale; the journal entries are the source of truth. **Openness = "no LIVE clearing JE links this bill"** (`matchableOpenItems`, keyed on `import_metadata.payment_for`), **side = the A/R/A/P OFFSET code on the entry's leg** (`autoMatchBankLines`, not `type`), **already-cleared = a real posted payment JE exists** (not the flag). When a flag and the GL disagree, the GL wins — and the flag should be treated as a display hint to re-derive, never a gate. (Mirrors §12's "cash on hand is GL-derived" and "amount owed = `glAccountBalance(AP)`, not a flag sum.")
- ❌ **Composing the sentence that describes an action ALONGSIDE the action, instead of deriving it FROM the result.** ✅ **A USER-FACING STRING ABOUT WHAT THE SYSTEM DID MUST BE GENERATED FROM THE RECORDED OUTCOME (recorded 2026-08-27, O115/O114/O128).** A description assembled in parallel with the work **can diverge from it** — and when it does, **the books are right and the user is misinformed**, which is the worst combination available: nothing is broken, so nothing gets fixed.
  - **THREE INSTANCES IN ONE WEEK, ALL THE SAME SHAPE:** *(1)* *"Lone Star $1,344.85 **as a client meal**"* while the ledger said **5000 COGS** (`O115`) · *(2)* **`MULTIPLE_CANDIDATES` invented as a reason** when the real cause was a failed write — a claim about the LEDGER that was false, and it made a whole drive undiagnosable · *(3)* **"✓ 0 invoices booked · $0.00 total"** for the most valuable outcome the feature produces (`O128`).
  - **★ THE STRUCTURAL SIGNATURE, and it is greppable: THE STRING READS THE INTENT, NOT THE RESULT.** Every instance takes the **pre-write invoice object** and re-computes from it, rather than reading **the entry as recorded**. `invoiceResult` (`App.jsx:4273`) carries **two of the three in twelve lines** — `invoiceCount: highConfidence.length` is blind to `attached` (3), and `bookedAs: plainCategoryPhrase(firstBooked)` re-derives a category the account already states (1). `describeBooking` (`clarify.js:176`) is a third carrier of the same call.
  - **THE CHECK: FOR EACH CLAUSE, NAME THE FIELD OF THE OUTCOME IT READS.** If a clause is computed from the **input**, it is a parallel description and **will** diverge — the only question is when. *"Booked as X"* must read the booked account. *"N booked"* must count what was written. *"Because Y"* must read the recorded reason.
  - **★★ ALL THREE INSTANCES FIXED 2026-08-29 (C208), AND THE FIX HAS A SHAPE WORTH REUSING: MAKE THE SENTENCE A PURE FUNCTION OF THE RECORD.** *"Every clause must read a field of the outcome"* is a rule nobody can check while the sentence is a closure inside a JSX block. `invoiceOutcomeCopy` (`src/lib/uploadOutcome.js`) takes the outcome as its ARGUMENT, so a test can assert it cannot reach the categoriser, the chart, or a raw `gl_code` — the same move `drainProgressCopy` made for the queue. **A description that cannot see the input cannot drift from the result.**
    - **`O115`** — `plainCategoryPhrase` keyword-matched the vendor BEFORE consulting the booked account. **★ AND THE FIX IS NARROWER THAN "NEVER READ THE TEXT" — two existing tests went red and were RIGHT.** `6400 Travel & Entertainment` genuinely spans two everyday things, so a caterer on that account being "a client meal" **refines** the account rather than contradicting it. The rule is **the account fixes the category; text may only refine WITHIN it**, refinements are declared per-role in `ROLE_REFINEMENTS`, and a test pins its exact contents — widening it silently is how the vendor's name gets back to overruling the account.
    - **★ HALF OF `O115` WAS AN ABSENCE, NOT A WRONG RULE:** the code→role map had **no 5xxx range at all**, so a COGS entry had no account answer to give and fell through to the text by default. And the name fallback reused `ANSWER_MAP` — the vocabulary of **what a human types** ("it was a flight"), which knows nothing of "Cost of Goods Sold". Account names now have their own map, **built from `DEFAULT_CHART_OF_ACCOUNTS` rather than retyped** — a fourth hand-copy of the chart would be `O125`'s mistake in a different column.
    - **`O128`** — `invoiceCount` counts only what was BOOKED, so a file whose invoices all matched existing payments rendered *"✓ 0 invoices booked · $0.00 total"*. Now names the vendor, amount and consequence, and survives alongside bookings and questions.
    - **`O124(c)`** — `softDeleteInvoices` claimed success without checking `allIds.length`. **★ AND THE OPTIMISTIC REMOVAL MADE IT WORSE, WHICH WAS NOT IN THE ORIGINAL FINDING:** rows were filtered out of `invoices` BEFORE the write, so a refused delete also **looked** done — the entry vanished from the screen while remaining in the books, and the next reload resurrects it. Rows are now restored, the failure audited, and the sentence says what to do about it.
  - **★★ THIRD RULE IN ONE FAMILY, AND THEY ARE A LADDER:** **name the reader** — the write does not land · **an invisible action will be repeated** — the effect lands but is not seen · **describe from the record** — the effect lands, is seen, and is described wrongly. **Each is harder to detect than the last**, because each one looks more like success.
- ❌ **Shipping an action whose effect the user cannot see.** ✅ **AN ACTION WHOSE EFFECT IS INVISIBLE WILL BE REPEATED (recorded 2026-08-27, O123/O124).** Not *may* be — **will**. A user who cannot tell that a thing happened has exactly one move left, and it is to do it again. **Cost already paid: three reversals against one invoice, −937.00 on one vendor**, from a user clicking a Void button whose effect was real, correct, and completely invisible on screen.
  - **THE FOUR INSTANCES, all live, all the same shape:** *(1)* **void leaves no visible marker** — the original stays listed and looks identical to a live entry (correct GAAP, §12 #14; the missing MARKER is the defect) · *(2)* **the Void control stays enabled** on an already-reversed entry, so the UI invites the repeat it should refuse · *(3)* **`softDeleteInvoices` says "Deleted" without checking whether the write landed**, so a blocked or failed delete is indistinguishable from a successful one · *(4)* **the SAFE action is four steps deep behind a filter label while the dangerous one is on the landing screen** — so invisibility of the *option* pushes the user onto the destructive path.
  - **★ IT IS THE USER-FACING TWIN OF "NAME THE READER".** That rule catches a write whose effect is invisible **to the system**; this one catches a write whose effect is invisible **to the person**. Same defect, two layers, and **the second is worse because a human responds to silence by retrying** — where an unread field merely sits there, an unseen action compounds. *(C195(7) is the same shape a third time: a guard whose input is always empty is indistinguishable from a clean queue.)*
  - **THE CHECK: after this action succeeds, what CHANGES ON SCREEN? Name the pixel.** If the answer is "a toast that disappears", it is invisible — **a transient confirmation is not a state change.** And **if the action is now impossible, DISABLE the control**; refusing on click is strictly worse than not offering, because it teaches the user that clicking is how you find out.
- ❌ **Shipping a limit, gate or threshold whose PURPOSE nobody can state.** ✅ **NAME THE THREAT, THE WAY YOU NAME THE READER (recorded 2026-08-26, O97).** *Operator: **"a limit nobody can explain the purpose of is the same class as a field nobody reads."*** Both are machinery that runs forever while nobody can say what it accomplishes — and **an unexplained limit is worse than an unread field, because it does not merely fail to help, it actively refuses work.**
  - **THE CASE: `AI_LIMIT` / `UPLOAD_LIMIT`.** Migration `021`'s header states **what** they are and never **why**. `ai-proxy`'s header does the same. The purpose is stated **exactly once in the whole repo**, in §7: *"limits prevent abuse/runaway cost"* — **two different threats, joined by a slash, implying two different mechanisms, neither of which the current design is shaped for.**
  - **THREE CANDIDATE THREATS, AND THE UNIT ONLY FITS ONE:**
    1. **RUNAWAY COST** → the unit should be **tokens or dollars, not requests.** Today a 20-token `classify-document` and a 4,000-token `extract-invoices-batch` **cost the same against the budget** — a 200× miscalibration. As a cost control it caps the wrong quantity.
    2. **UPSTREAM PROVIDER LIMITS** → Anthropic's are **org-wide and per-minute**. A **per-user, per-hour** cap does not defend them at all: ten users at 59/hour each can spike hundreds of requests into one minute while every one of them is "under". **Wrong scope and wrong window.**
    3. **ABUSE — a compromised or malicious authenticated account burning the key** → **per-user-per-hour is exactly right.** Bounded blast radius per account, and the account is the thing you can revoke.
  - **★ SO THE LIMIT IS WELL-SHAPED FOR (3) AND BADLY SHAPED FOR (1) AND (2) — AND IT IS CURRENTLY BEING ENFORCED AGAINST A LEGITIMATE FIRST-TIME ONBOARDING, WHICH IS NONE OF THE THREE.** That is the product working as designed, refused by a mechanism built for someone attacking it. **Naming the threat is what makes that visible**; while the purpose stayed a slash in one sentence, the only available move was to argue about the number.
  - **THE CHECK, and it is the same shape as "does this actually route?": *what specifically goes wrong if this limit is absent, and is the quantity I am counting the quantity that goes wrong?*** If the threat is cost, count cost. If it is upstream, match upstream's scope and window. If it is abuse, per-actor is right — **and then a legitimate bulk workload needs a different door, not a bigger number.**
- ❌ **Writing a field to route something, without naming the reader that will act on it.** ✅ **FOR EVERY FIELD WE WRITE IN ORDER TO ROUTE SOMETHING, NAME THE READER — AND CHECK THE VALUE DOESN'T DEFEAT IT (recorded 2026-08-26, O114).** A write that succeeds and a routing that happens are two different events, and **the write's success is not evidence of the routing.** There are two shapes and the second is nastier:
  1. **NO READER EXISTS.** The field is written faithfully forever and nothing consults it. **`import_metadata` (O87/·3a)** — `post_journal_entry` cherry-picks six named scalars out of `p_meta` and never writes `import_metadata` at all, so the payroll auto-post gate read it, found nothing, and **failed closed for an entire release** while a green suite reported health. Same mechanism silently disabled the O59 sales-tax control and `signedPeriod`'s `original_date`.
  2. **★★ A READER EXISTS AND THE WRITTEN VALUE GUARANTEES IT SAYS NO. "A VALUE THAT SATISFIES THE WRITE AND DEFEATS THE READ IT WAS WRITTEN FOR."** **The duplicate card's "Not sure" branch (O114)** stamps `approval_status: "flagged"` and `duplicate_flag: true` — read by a detail panel and an unrelated AP screener, by nothing in the review queue — **and books at `confidence: 100`, which is precisely the value that makes `shouldFlagForReview` return `none`.** So the option that *looks* like "send this to a human" **books the expense and then guarantees no human sees it.** Worse than an inert path: an inert path does nothing, this one acts and hides.
  - **★★ THE CHECK IS A QUESTION, AND THE QUESTION IS THE RULE — NOT A PARAPHRASE OF IT. ASK IT OUT LOUD, AT WRITE TIME:**
    > ### *"Does this actually route?"*
    > *Who reads this field, at what `file:line`, and what would they do with the exact value I am about to write?*
    - **If the answer is a `file:line`, it routes. If it is a table name, a status string, or a hopeful adjective, it does not.**
    - **Where the reader is a THRESHOLD, write the value that TRIPS it.** `confidence: 100` on a row you want reviewed is a request to be ignored.
  - **★★ AND WHY THIS CANNOT BE DELEGATED TO THE SUITE: A TEST ASSERTS A VALUE WAS WRITTEN. ONLY TRACING THE READER PROVES THE WRITE DOES ANYTHING.** Both instances above sat behind green suites — `import_metadata` for an entire release, `confidence: 100` for longer — and **neither was found by a test. Both were found by a human asking the question. Twice this month.** A test that asserts `approval_status === "flagged"` passes forever on a field nobody reads; it is verifying the writer against itself, which is the same shape as ·3a's extractor and fixture agreeing while neither agreed with the database.
  - **CHEAPEST DETECTION, in order: (1) `grep` for the reader before shipping the writer** — one command, and it answers the question definitively; **(2) prefer asserting the mechanism FIRES over asserting nothing is outstanding** (C195(7) — a guard whose input is always empty is indistinguishable from a clean queue); **(3) where the field is a routing decision, assert a POSITIVE COUNT downstream**, not an absence upstream.
- ❌ **Counting a human's answer as evidence for a question they were not asked.** ✅ **AN ATTESTATION IS SCOPED TO THE QUESTION THAT WAS ASKED (recorded 2026-08-26, O114).** A click is evidence about **the thing the human was looking at**, and nothing else. Promoting it to evidence about an adjacent fact is the machine laundering its own guess through a human's hand — the guess acquires a person's authority without a person ever having considered it. **TWO INSTANCES, WHICH IS WHY IT IS A RULE AND NOT A PATCH:**
  1. **Amendment B** (`docs/CALIBRATION_SPEC_O88_AMENDMENT_B.md`, signed 2026-08-25) — **signing a month is not examining a vendor.** A sign-off attests the period as it stood; it does not attest that each vendor's account was inspected. Backfill graduation therefore requires an EXPLICIT attestation, and on current data that graduates **0 of 13**.
  2. **O114** (`docs/INVOICE_PAYMENT_SPEC_O114.md`) — **answering a duplicate/ambiguity card is not attesting a mapping.** The question is *"are these two documents the same purchase?"* — document identity. The human need not have seen the account, and attaching does not change it. Without the exclusion, `attestationStrengthFor` grades the resolution EXPLICIT, Amendment B's bar is met, and **a vendor graduates to KNOWN on PAPERWORK VOLUME** with `attested_account_id` set to whatever the machine booked — routing around the amendment within one release of it being signed.
  - **THE MECHANISM, so the third instance is caught rather than rediscovered: grade on the EXCEPTION KIND, never on the bare fact that a human clicked.** `NON_ATTESTING_EXCEPTIONS` (`vendorBackfill.js`) is a SET for that reason, and a test asserts its **exact contents** — widening it silently is how the bar would disappear. **A RECODE always attests** (the human looked at the account and changed it); when a resolution both matches and recodes, that is **two facts**, and only the recode touches the familiarity clock.
  - **AND THE COROLLARY THAT MAKES IT ACTIONABLE:** before recording any human action as evidence, write down the question they were actually shown. If the fact you want to record is not an answer to that question, it is not attested — it is inferred, and it must be graded IMPLICIT and say so.
- ❌ **A row-targeted `.update()` without `.select()`, and an empty `catch {}` around a write.** ✅ **Row-targeted mutations go through `checkedRowUpdate` (`checkedWrite.js`) — ZERO ROWS IS A FAILURE.** PostgREST reports **no error** for an update that matched nothing, so without `.select()` (returning=representation) a broken write is indistinguishable from a successful one; an empty `catch {}` then swallows what little signal remains. This is the **root-cause class of two live O84 bugs** — C191 (planner exceptions carried a non-DB id → every `.eq("id", …)` matched zero rows → five lines silently stayed 'pending') and C189 (the payroll entry never got `payment_status`, invisible until an `ap_tie` control total failed by $4,306). Both would have been **one loud console line** under checked writes. Doctrine: **(1)** row-targeted mutations go through `checkedRowUpdate` / `checkedIdsUpdate` (assert no error AND rows-affected ≥ 1; loud `console.error` + a counted failure record); **(2)** **ids reach DB calls ONLY through `lineDbId` / `resolveLineDbId`** — never a raw parse-time id (grep-enforceable); **(3)** **empty `catch {}` around a write is forbidden** — log it or count it; **(4)** every new write path stamps the hygiene fields (`payment_status`, `bank_account_id`, `meta.kind`).
- ❌ **A write path that creates a CASH-SETTLED entry but omits `payment_status` `'paid'`.** ✅ **Every write path that posts a cash-settled entry must stamp `payment_status: 'paid'`** (via `meta` → `post_journal_entry` → `flattenJournalEntries`). The sub-ledger heuristics `apUnpaid`/`arUnpaid` (`reports.js`) TRUST that field — `apUnpaid = isExp && payment_status !== 'paid'` — so a path that omits it lets the entry's **expense legs leak into the open-bills universe**, failing the `ap_tie` control total (Review shows "1 figure that should match but don't", Home downgrades) **while the GL itself is perfectly correct**. C189 (O84): PayrollView's post path posted a correct 4-leg payroll entry with no `payment_status`, so Salaries + Payroll Tax Exp leaked and `ap_tie` failed by exactly gross+employer ($4,306). Root cause is **write-path hygiene divergence** — the bank-line payroll path stamped it (`buildBankLineEntry`: `payment_status: "paid"`), the PayrollView path didn't. The heuristic is correct; the writer was wrong. (Payroll's withholding LIABILITY is tracked by its own GL — Payroll Taxes Payable — not the bills list, so stamping the whole entry paid is right.)
- ❌ **Keying bank re-upload dedup on TEXT or GL code (vendor / description / gl_code).** ✅ **`bankTxnKey` = `date | abs(amount) | direction` only** (`openingBalanceProposal.js`). O83 production: re-uploading a statement double-booked 14 of 20 lines because the key mixed the CLEANED vendor (booked side: `"Toast POS"`) with the RAW memo (re-parse side: `"TOAST POS DEPOSIT 011326"`), and the GL even re-categorized run-to-run ($15 fee `8000`→`7100`) — so text/GL keys are asymmetric and never collide. **Known trade-off (accepted):** two genuinely-distinct same-day/same-amount/same-direction lines collide; failure mode is a real new line arriving FLAGGED already-booked (defaulted UNCHECKED in review — visible, one click to re-check), never a silent double-post. Safer than the text key that shipped the bug.

## 12. GAAP correctness as tested code

Every economic event's journal entry must be a **pure `buildXEntry()` in a lib module with a unit test asserting exact Dr/Cr/amount, routed through the handler — never built inline in a view or by the AI.** `tests/gaapInvariants.test.js` is the living spec/guardrail: over a fixture of every event it asserts (a) Dr = Cr, (b) Assets = Liabilities + Equity + NetIncome, (c) payments/collections/opening/reversals leave net income unchanged, (d) only 4xxx/5–8xxx move net income. The AI may **reason and explain** with GAAP knowledge but **only executes whitelisted actions** (`aiCapabilities.js`); it never constructs raw entries.

**The 17-event inventory** (status tracked in the guardrail/remediation): 1 book bill, 2 pay bill (✅ Step 1), 3 direct-to-cash, 4 issue invoice, 5 collect (✅), 6 opening balances, 7 bank/cash opening, 8 depreciation, 9 prepaid capitalize+amortize, 10 accrued liabilities, 11 deferred-revenue receipt+recognition, 12 lease (ASC 842), 13 payroll, 14 void→reversing entry, 15 reversal, 16 sales tax, **17 year-end closing** (Dr each Revenue / Cr each Expense / plug net to Retained Earnings 3100; zeroes the period's P&L; new year starts at zero).

**Fiscal-year / Retained-Earnings model (built — derived soft close, Option A):** `reports.js` `fiscalYearSplit(invoices, {asOf, fiscalYearEnd, cutoffDate})` (+ pure `fiscalYearStart`) splits all-time net income into prior-fiscal-years' closed net (→ **beginning Retained Earnings**, always shown as a distinct line) and the current FY's net (→ **Net Income (current period)**), keyed off `companies.fiscal_year_end` and floored at `cutoff_date`. The Balance Sheet shows the two as separate lines summing to Total RE; `priorNet + currentNet === all-time net`, so every total and the balance check are unchanged — only the RE split. This fixes the pre-fix bug where a prior-year (e.g. 2024) loss was mislabeled "current period" and the Balance-Sheet net income diverged from the Income Statement from a client's 2nd fiscal year on. Guardrail: `gaapInvariants.test.js` "fiscal-year RE split" asserts prior+current=all-time, the year-boundary case (prior loss → beginning RE, not current), FYE handling, and cutoff flooring. No posted closing entries required (that's the deferred hard close, #17).

### Governing principles (conversion & cash)

- **Clean cutoff date ("Day One").** Each company has one `companies.cutoff_date`. The entire starting position is **one balanced opening journal entry** as of the cutoff — the prior trial balance (assets, liabilities, already-accumulated retained earnings), plugging the residual to **Opening Balance Equity (3400)**. **No transaction may be dated before the cutoff**; pre-cutoff activity is represented solely by opening balances. This makes the retained-earnings double-count structurally impossible. Enforcement is **hybrid**: `persistJournalEntry` hard-rejects pre-cutoff bookings with a redirect ("record it by adjusting your opening balances"); imports skip pre-cutoff rows; posting opening balances is hard-blocked if live pre-cutoff transactions exist (`preCutoffActivity`); legacy companies with no cutoff get no enforcement (warn-only). The cutoff is editable until the opening entry is posted, then **locked**. Opening balances post through the canonical path (`buildOpeningBalanceEntry` → `post_journal_entry`, `source='opening_balance'`) **and** persist to the `opening_balances` table (`journal_entry_id`, `posted=true`); `loadAllData` reads them back so they survive refresh. Editing = reverse/replace (soft-delete the prior opening JE + rows, repost) — never duplicate.
- **Bank-as-source-of-truth.** A bank account's `current_balance` IS the opening balance of that bank's cash GL account. It flows through the **same** opening entry (Dr that bank's cash GL / Cr OBE), keyed by GL account; bank-linked cash accounts are shown **read-only** in the opening-balances grid (valued from the bank), so no GL account is opened twice. A cash balance is never a free-floating field invisible to the GL.
- **The QBO-import model is the same** (item 43): trial balance at the cutoff as the opening entry, then live transactions forward — not bulk pre-cutoff history. Keep them consistent.
- **Cash on hand is GL-derived (single source).** Every displayed cash figure (dashboard card, runway, health score, KPIs, monthly report, AI snapshot) derives from `reports.js` `glCashOnHand(invoices, cashCodes, {asOf})` = Σ `glAccountBalance` over the cash/cash-equivalent accounts (roles `cash`+`savings` + bank-linked GL codes), computed once in `ERP` as `glCash`. So dashboard cash === Balance Sheet cash line === `glAccountBalance(cash)` by construction. `computeCashPosition` and the ad-hoc runway-drill formula were removed. The **bank statement balance** (`bank_accounts.current_balance`) is kept but only as the reconciliation target (what the bank says) — never the displayed cash on hand (what the books say); a difference is a reconciliation item.
- **Parallel P&L derivations are lock-tested, not rewritten (cluster #4).** `computeRevenue/Expenses/NetIncome` and `trialBalance` already re-derive from the ledger (sum of entries), so they were left as-is rather than rewired through `glAccountBalance` (lowest-severity, highest-blast-radius). `reconciliation.test.js` "cluster #4 lock" asserts they EQUAL the `glAccountBalance` derivation (revenue = Σ over 4xxx, expenses = Σ over 5–8xxx, net income, and trial-balance per account), so any future drift between the two derivation paths fails CI. (The previously-known nuance — revenue/expense booked on an entry's *offset* leg would diverge — is now **resolved** by the Phase 0 flatten fix below: the P&L line is always the primary `gl_code`, so `computeRevenue`/`Expenses` and `glAccountBalance` agree even for `Dr A/R · Cr Revenue` and `Dr Deferred Rev · Cr Revenue` entries.)
- **AR mirrors AP (cluster #2, built).** AR Outstanding (Dashboard, ArView, AR aging total) reads `glAccountBalance(accounts_receivable)` — the same single GL source as AP. Collecting an invoice posts `Dr Cash / Cr AR` through the canonical `markBillPaid(side:"ar")`/`buildPaymentEntry`; the flag-only/local-only collection paths were fixed (SendInvoiceView "mark paid", bank auto-match, and `applyMatch` full matches all route through it; partial matches stay flag-only pending a partial-clearing feature). `planArBackfill` + `040_ar_collection_backfill_oneshot.sql` exist and are tested (symmetric to AP `039`) but are a **no-op on current data** (dry-run showed zero candidates) — kept for a future real-client conversion.
- **AP / GL-balance single source (AP Step 2, built).** `reports.js` `glAccountBalance(code, invoices, {asOf})` is THE canonical GL balance of any account (sum of its journal-entry-line movements, normal-balance signed; primary leg + offset leg for simple entries; multi-line `_` rows primary-only). The Balance Sheet (`getBal`), the Payables "Outstanding" total, and the Dashboard AP total all read it, so they reconcile by construction. "Amount owed" = the GL balance of Accounts Payable (not a `payment_status`-flag sum); the flag still drives the per-bill paid/unpaid LISTS for display. NOTE: the AR/AP **aging** report and the AI `computeAP` remain payment_status/due_date views (aging needs them); they fully converge with the GL only after **AP Step 3 (historical backfill)** posts the missing Dr-AP/Cr-Cash entries for bills marked paid before Step 1. So post-Step-2 the GL-based surfaces MATCH each other but aren't yet CORRECT until Step 3.

- **Depreciation (#8, Phase A, built).** Capitalizing a purchase now creates a real `fixed_assets` master + a generated `depreciation_schedule` (migration `041`), replacing the dead `needs_depreciation` flag (which never produced an entry). Capture: the GAAP clarification's capitalize option carries an **AI-suggested useful life** (`suggestUsefulLifeMonths` — buildings 39yr, vehicles/tech 5yr, furniture/equipment 7yr, default 5yr), overridable in the confirm step along with **salvage (default $0)** and **in-service date (defaults to purchase date)**. `createFixedAssetWithSchedule` inserts the asset + pending monthly rows from `buildDepreciationSchedule` (straight-line; last month absorbs rounding so Σ === cost − salvage exactly). **"Run depreciation through DATE"** (ReportsView control → `runDepreciationThrough`) posts every pending row due on/before the date as `Dr 6900 / Cr 1510` through the canonical multi-line path, stamps it `posted` + links the JE, and **auto-flips the asset to `fully_depreciated`** once its last pending row posts (`planDepreciationRun` decides due-rows + flips, purely). Idempotent (only pending rows). Lib `src/lib/depreciation.js`; pure builders + the run-planner are unit-tested (`tests/depreciation.test.js`: suggestion, schedule sums-to-base, periodic posting, fully-depreciated flip) and `buildDepreciationEntry` is wired into the gaapInvariants guardrail (#8). Deferred variants (declining-balance/units-of-production/MACRS) noted below.
- **Canonical multi-line write path (Phase 0, built).** Multi-line economic events (deferred-revenue recognition #11b, prepaid amortization #9, lease commencement #12, and going forward payroll #13 + sales-tax invoices #16) post as **ONE balanced journal entry with N lines** through `buildJournalEntry({lines})` (`src/lib/journalEntries.js`, pure + tested) → `persistMultiLineEntry` (`App.jsx`, resolves codes→ids and calls `post_journal_entry` once). This **replaces the per-line expansion** in `postContractEntry`/`postAllContractEntries` that posted each line as its own 2-line JE — an active **double-count** bug (a 2-line recognition entry posted revenue on both a primary and an offset leg → 2× revenue). Contract posting now builds one entry per contract JE, refuses unbalanced entries, and reloads to reflect the single posted entry. Paired fix: `flattenJournalEntries` now picks the **P&L line as primary `gl_code`** for simple 2-line entries (was first-debit), so revenue/expense never strands on the offset leg — this is what makes `computeRevenue`/`Expenses` agree with `glAccountBalance` (and repairs the latent post-reload bug where `Dr A/R · Cr Revenue` flattened with A/R as primary). Lock: `tests/multiLineEntry.test.js` runs the **real** `flattenJournalEntries`→derivation path and asserts on a deferred-revenue fixture that `computeRevenue === glAccountBalance('4200') === 500` (the agreement) and that posting once yields 1× not 2× (no double-count); `tests/journalEntries.test.js` covers the builder (balance, N-line, zero-line drop, cent rounding, unbalanced→refused).

**Standard variants deliberately deferred (industry-standard common case built first; full variants are known, not silently missing):**
- **Sales tax (#16):** built = single blended rate on outgoing AR invoices, `Dr A/R / Cr Revenue / Cr Sales Tax Payable (2350)` (sales tax is a liability, never revenue). **✅ PER-LINE RATES AND A JURISDICTION BREAKDOWN ADDED 2026-08-30 (C267)** — `computeLineTax` + `buildArInvoiceEntryPerLine`. The single-rate builder is unchanged and still the default. **The universal-upload sales path remains deferred.**
  - **★★★ THE FAILURE A BLENDED RATE PRODUCES IS THE DANGEROUS KIND: THE INVOICE TOTAL CAN BE RIGHT WHILE THE SPLIT IS WRONG — AND THE SPLIT IS WHAT GETS FILED.** You remit to a jurisdiction, not to an average. **An invoice collecting the correct $86.25 and attributing it to the wrong state is a correct-looking document and a wrong return.**
  - **★★ THE BREAKDOWN IS CARRIED, NOT COLLAPSED.** The GL still credits ONE Sales Tax Payable — a liability account per state needs a migration and is a bigger decision — but the per-jurisdiction amounts ride in the entry's meta, **so a return can be prepared FROM THE BOOKS rather than reconstructed from invoices. Collapsing them at booking time destroys the only place that fact exists.** A test asserts the breakdown always sums to the tax charged.
  - **★★★ EXEMPT, ZERO-RATED AND MISSING ARE THREE DIFFERENT THINGS.** An exempt line (a restaurant's grocery items) is a **decision someone made** and contributes nothing. A stated **0%** is honoured. **A MISSING rate refuses the whole invoice** — treating it as zero would under-collect silently and produce an invoice that looks complete. **The one thing worse than asking is guessing.**
  - **★ THE TOTAL IS UNCHANGED BY DESIGN**, because `C241`'s accuracy control cross-foots *"tax charged"* against the Sales-Tax-Payable balance — **adding jurisdictions must not quietly move the figure that check compares.**
- **Depreciation (#8):** built = **straight-line** monthly schedule, `Dr Depreciation Expense (6900) / Cr Accumulated Depreciation (1510)`. **✅ DECLINING-BALANCE AND UNITS-OF-PRODUCTION ADDED 2026-08-30 (C265)** — pure curves in `depreciationAmounts`, straight-line unchanged and still the default. **MACRS and mid-year conventions remain deferred** (they are tax-table lookups, not curves, and belong with tax work rather than here).
  - **★★★ THE INVARIANT THAT MAKES A METHOD SAFE TO ADD: every schedule sums EXACTLY to cost − salvage.** An asset must be written down to its salvage value and never past it, whatever curve it takes. **Over-depreciating writes off value the business still owns; under-depreciating leaves a stub nobody notices.** Six method/base/period combinations assert it to the cent, including bases that do not divide evenly.
  - **★★ DECLINING BALANCE SWITCHES TO STRAIGHT-LINE, AND THE SWITCH IS NOT AN OPTIMISATION — WITHOUT IT THE ASSET NEVER FINISHES.** The method takes a fraction of what is LEFT each period, so it approaches zero and never arrives; the schedule would end with a stub still on the books. The flat tail (`4000 2400 1440 1080 1080`) **is** the switch, visible in the numbers.
  - **★★ UNITS-OF-PRODUCTION REFUSES WITHOUT THE USAGE RATHER THAN FALLING BACK.** The method exists to measure actual use; a straight-line fallback would produce a schedule that **looks like usage-based depreciation and is not — a wrong answer wearing the right label.**
  - **★ AND AN UNRECOGNISED METHOD FALLS BACK TO STRAIGHT-LINE, pinned to the LITERAL curve.** The first version of that test compared the unknown method to `STRAIGHT_LINE`'s output — **both moved together under a mutation and it passed.** Two sides of one contract checked against each other is the `·3a` shape: it proves they agree, never that either is right.
- **Payroll (#13):** built = standard multi-line `Dr Salaries (gross) / Dr Payroll Tax Expense (employer) / Cr Cash (net pay) / Cr Payroll Taxes Payable (withholdings + employer)`, net pay → Cash (assumes already disbursed). **✅ THE ACCRUE-THEN-PAY TWO-STEP ADDED 2026-08-30 (C266)** — `buildPayrollAccrualEntry` + `buildPayrollDisbursementEntry`. The one-step case is unchanged and still the default; the split matters **whenever the pay period ENDS in one month and the money leaves in the next** — the expense belongs to the period worked, the cash to the day it moved.
  - **★★★ THE ONLY INVARIANT WORTH TESTING HARD: THE TWO ENTRIES TOGETHER ARE EXACTLY THE ONE-STEP ENTRY.** Same expense, same liability, same cash, same totals, and the intermediate liability **closes to zero**. If they differed, a company would get **a different P&L for choosing a different bookkeeping convention on identical facts — not a variant, a bug with a preference setting.**
  - **★★ THE DISBURSEMENT TOUCHES NO EXPENSE ACCOUNT, and a test asserts no 4xxx–8xxx line can appear in it.** If it could move net income the expense would land **twice** — once accrued, once paid — and the P&L would be wrong by a full payroll in the month the money left.
  - **★ THE ACCRUAL REFUSES WITHOUT A LIABILITY ACCOUNT rather than falling back to cash.** A fallback would silently produce the ONE-step entry under a TWO-step name, and the caller would believe the expense and the cash had been separated when they had not.
  - **★★★ AND THE FIXTURE HAD TO GROW AWKWARD NUMBERS, BECAUSE A ROUNDING MUTATION SURVIVED THE ROUND ONES.** Flooring the accrual's net pay left every assertion green — 3150 is already whole. **Rounding is precisely where two independent paths diverge**, so the invariant is now re-asserted on `4133.33 / 316.21 / 3211.07` and three more, including a 3-cent run. *(Also recorded: an earlier mutation reported "no tests" rather than red — it referenced a parameter that does not exist and broke the module. **A module that fails to load is neither a pass nor a fail, and must not be counted as either.**)*
